# astro-template

A personal Astro starter built on top of the official
[withastro/astro](https://github.com/withastro/astro) **"minimal"** example,
kept in sync with upstream and stamped with a set of patches.

## Usage

```sh
pnpm create astro@latest -- --template gpnka/astro-template
```

## Why there are two branches

| Branch  | Role |
|---------|------|
| `sync`  | Source of truth for the sync setup: `.github/` (workflow, Renovate config, `UPSTREAM_SHA`) and `patches/`. **This is where you edit** |
| `main`  | Generated output: upstream example at `UPSTREAM_SHA` + applied patches. **Never edited by hand** — the workflow rewrites it |

Cloud-hosted Renovate watches the `sync` branch and opens a PR whenever
upstream moves; once merged/pushed, the workflow regenerates `main`.

## How the sync works

`.github/workflows/sync-and-patch.yml` runs on push / PR to `sync` that touches
`.github/UPSTREAM_SHA` or `patches/**`:

1. Reads the target commit from `.github/UPSTREAM_SHA`;
2. Fetches that exact commit from `withastro/astro`;
3. Resets the working copy to it;
4. Applies each file from `patches/` in name order (`00_`, `01_`, …) as one
   commit each — `.sh` scripts are executed, `.patch`/`.diff` go through
   `git apply`; anything else (e.g. `README.md`) is ignored;
5. Force-pushes the result to `main`.

See `patches/README.md` for what each patch does.

## Keeping upstream current

The pinned SHA lives in `.github/UPSTREAM_SHA` — it is expected to be the tip
of the `examples/minimal` branch of `withastro/astro` (generated from their
`main`, commits carry messages like `Sync from <main-sha>`).

`.github/renovate.json5` tracks that branch via the `git-refs` datasource.
Because the config lives on the `sync` branch — not the default branch — hosted
Renovate will **not** discover it on its own. Point it at the config:

1. Open the **[Mend developers dashboard](https://developers.mend.io)**;
2. Select this repository;
3. Go to **Credentials** → **Repository variables**;
4. Add a variable:

```
RENOVATE_EXTENDS: "local>gpnka/astro-template//.github/renovate.json5#sync"
```

When a new upstream SHA appears, Renovate opens a PR against `sync`; merging it
triggers the workflow, which regenerates `main`.

## Setting sync up for your own fork

If you fork this repo (or use it as a template) and want the same
upstream-syncing Renovate to run against **your** repository:

1. Use the template — `sync` and `main` come along as they are.
2. Point Renovate (in the Mend dashboard, **Credentials** → **Repository
   variables**) at the config **in your repository**:

```
RENOVATE_EXTENDS: "local>YOUR_USER/astro-template//.github/renovate.json5#sync"
```

3. That's it — Renovate's `git-refs` update will now open PRs against your
   `sync` branch, and the workflow will rebuild your `main`.

**Can the path be "universal"?** The `local>` preset is bound to one
owner/repo, so it can't be fully owner-agnostic. If you don't customize the
config, leave the canonical path (`gpnka/astro-template`) as-is and every fork
keeps working off the same string. Only swap in your own owner/repo when you
actually maintain a diverged config in your own fork.

> Note: if you don't want to configure the dashboard at all, you can commit a
> `renovate.json` into your default branch that just extends the preset:
>
> ```json
> { "extends": ["local>gpnka/astro-template//.github/renovate.json5#sync"] }
> ```
>
> But with this setup the default branch is regenerated by the workflow, so the
> file would have to be shipped via a patch to survive syncs.
